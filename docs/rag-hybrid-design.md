| 配置 | Recall@1 | Recall@3 | **Recall@5** | Precision@1 | MRR |
|---|---|---|---|---|---|

## 1. 背景与目标

改造前检索是单路稠密向量:`Chroma 查询 top-4 → 拼进上下文`。摸底测试(§4)显示
Recall@5 仅 0.72、top-1 准确率 0.52——约 1/4 的问题根本召不回正确知识块,一半的问题
top-1 不是最相关知识。JDDC 语料是真实客服口语("额 那怎么办 机器动力不足还不就是机芯
有问题?"),错别字、语气词、词序多变,纯向量对型号/专有名词等词面信号也不敏感。

目标(本期):**Recall@5 ≥ 95%**,同时改善排序质量(top-1/MRR),且检索链路可评测、
可复现、超参数可再调。

## 2. 设计路线

### 2.1 目标架构

```
用户问题(query)
   │
   ├─ 稠密路:embedding-3 → Chroma 近邻,top DENSE_TOPK=50        ┐
   │                                                             ├→ 融合(min-max 加权,α=0.5)
   ├─ 稀疏路:jieba 搜索粒度分词 → BM25Okapi,top BM25_TOPK=50     ┘      │
   │                                                             融合池 top RERANK_CANDIDATES=20
   │                                                                     │
   │                                                    交叉编码器重排(智谱 rerank API)
   │                                                                     │
   └───────────────────────────────────────────────  top HYBRID_FINAL_K=5 → LLM 上下文
```

### 2.2 关键选型与理由

| 决策点 | 选择 | 理由 |
|---|---|---|
| 稀疏检索 | `rank-bm25` + `jieba.lcut_for_search` | 纯 Python、毫秒级构建(2504 块),无服务依赖;`cut_for_search` 的重叠切分利于召回;BM25 索引**启动时从语料内存构建**,不改 ingest |
| 融合算法 | 默认 **weighted(min-max 归一加权)**;备选 RRF | 网格实测 weighted 的 r@3/MRR 更优(0.92/0.882 vs RRF 最优 0.88/0.864);RRF 保留为名次型备选(`FUSION=rrf`,标准常数 k=60)。两路分数量纲不可比,weighted 前必须 per-query min-max 归一 |
| 重排 | **智谱 rerank API**(`POST /paas/v4/rerank`,`model="rerank"`) | 即交叉编码器即服务:实测可用(HTTP 200,relevance_score 返回正常),零本地依赖、免模型下载;单请求 ≤128 条/每条 ≤4096 字,20 候选一批发送 |
| 重排备选 | `local`:fastembed ONNX cross-encoder(默认 `BAAI/bge-reranker-base`) | 断网/比价 A/B 用,可选依赖组 `rerank-local`,不装不影响默认链路 |
| 降级开关 | `RERANK_PROVIDER=off`、`RETRIEVAL_MODE=dense` | off=只融合不重排;dense=完全回退旧行为,便于对照与回滚 |
| agent 接口 | `HybridRetriever` 暴露 LlamaIndex `retrieve/aretrieve → list[NodeWithScore]` | `agent.py` 的 `retrieve_knowledge` 工具与 SSE citations 链路**零改动** |

### 2.3 工程要点

- **进程级单例**:BM25 索引、语料、rerank 客户端只建一次(`get_hybrid_retriever()`),
  避免每请求重建(构建约 3-4s)。
- **单例锁必须可重入**:`get_hybrid_retriever()` 持锁调 `HybridRetriever.__init__`,
  后者 `get_corpus()` 会再次加锁——`threading.Lock` 同线程自死锁(本次冒烟排障的根因),
  必须用 `threading.RLock`(hybrid.py 有注释,勿改回)。
- **重排分数即引用分数**:citations 里的 score 现在是交叉编码器 relevance_score,
  语义比原来 Chroma 距离更直观。
- **过滤零分类**:稀疏路剔除 BM25 得分为 0 的块(与 query 无词面重叠),避免污染融合。

## 3. 超参数清单与调优方法

### 3.1 参数清单(backend/.env,均有缺省值)

| 参数 | 缺省 | 作用 |
|---|---|---|
| `RETRIEVAL_MODE` | hybrid | dense=旧纯向量;hybrid=混合链路 |
| `SIMILARITY_TOP_K` | 4 | dense 模式的召回条数(旧行为兼容) |
| `DENSE_TOPK` / `BM25_TOPK` | 50 / 50 | 两路各自召回深度(融合池大小) |
| `FUSION` | weighted | weighted=分数归一加权;rrf=倒数排名融合 |
| `HYBRID_ALPHA` | 0.5 | weighted 下稠密路权重(稀疏路=1-α) |
| `RRF_K` | 60 | RRF 平滑常数(仅 rrf 模式) |
| `DENSE_WEIGHT` / `BM25_WEIGHT` | 1.0 / 1.0 | rrf 模式下两路权重 |
| `RERANK_PROVIDER` | zhipu | zhipu / local / off |
| `RERANK_CANDIDATES` | 20 | 送入重排的融合候选数(重排成本主决定项) |
| `HYBRID_FINAL_K` | 5 | 重排后返回给 LLM 的块数 |

### 3.2 调优协议(scripts/tune_rag.py)

**核心思路:把贵的调用缓存起来,让网格里每个组合变成纯内存运算。**

1. **固定评测集**:从 kb.jsonl(2500 条 QA)按 `seed=42` 抽 **50 个去重问题**
   (过短剔除)。评测集与 gold 定义见 §4。
2. **一次性预计算**(每查询只做一次 API/重活):
   - 稠密路:embedding-3 查询向量 → Chroma 取 top-100 名次与距离;
   - 稀疏路:BM25 全量打分取 top-100;
   - 重排:两路 top-50 的并集(≤100 块)调一次 rerank API,**分数按
     `(qid, chunk_id)` 缓存**——50 次重排调用,之后网格内任意候选组合直接查表。
3. **网格**(全部内存运算):
   - 深度: dense/bm25 ∈ {(10,10),(20,20),(50,50),(50,10),(10,50)}
   - 融合: rrf k∈{5,10,30,60};weighted α∈{0.3,0.4,0.5,0.6,0.7}
   - 重排: off / {候选 10, 20, 50}
   - 共 9 种深度 × 9 种融合 × 4 种重排 ≈ 324 组合 × 50 题,秒级完成。
4. **选择准则**:先按 `Recall@5 ≥ 0.95` 过滤;达标者中优先**带重排**(top-1/MRR
   明显更好,且是目标架构)、再按重排候选数与召回深度取成本最低。
5. **产出**:全部组合指标 + 最优配置写入 `backend/eval/results/tune_*.json`,
   人工复核后把最优值写进 `config.py` 默认与 `.env.example`,并用
   `eval_rag.py` 走生产代码路径复评确认。

**调参经验(本次实测):**
- **召回深度最不敏感**:融合池 ≥10 就够了(重排负责排序,池子只要装得下 gold);
  真正卡上限的是重排质量。
- **重排是 top-1 的杠杆**:同配置开关重排,r@1 从 0.71→0.83、MRR 0.824→0.882。
- **重排候选数不敏感**:rc=10 与 50 的 r@5 相同(0.96),取 20 是给 r@3/MRR 留余量;
  它是 rerank token 成本主项,别盲目调大。
- **RRF vs weighted**:weighted 胜出但差距不大(α=0.5 中性最稳);语料换血后两个都重跑。
- **融合池覆盖上限**:top-50+top-50 并集对 gold 的覆盖率 100%(本次),它是整条链路
  召回的理论上限;若调优始终达不到目标,先查这个数,再查切分粒度。

## 4. 评测协议(摸底怎么测的)

- **查询**:kb.jsonl 抽 50 个去重问题原文(含语气词、错别字,即真实用户输入形态),
  `seed=42` 可复现;不人工筛题,保证反映语料真实难度。
- **gold 块**:Chroma 中**问题文本相同(去空白归一)的全部块**。ingest 按问答对建文档、
  元数据随块继承,2500 条 → 2504 块(仅 4 条长答案被切开),绝大多数问题恰对应 1 块;
  同题多块时 gold 取并集(更宽松、更公平)。
- **指标定义**(与 IR 惯例一致,`k` 为返回给 LLM 的块数):
  - **召回率 Recall@k**:gold 与 top-k 有交集的查询占比(单 gold 块时即命中率);
  - **准确率 Precision@k**:top-k 中 gold 块的平均占比(top-1 即"第一名是不是最相关知识");
  - **MRR**:首个 gold 名次倒数的均值(排序质量综合刻画)。
- 口径说明:这是**检索层**评测——Recall@5=0.96 意为"正确知识块出现在给模型的 5 块
  上下文中"的概率。端到端"回答正确率"≈ 召回 × 生成忠实度,生成侧归 Phase 2 的
  RAGAS 评测(见 agentic-rag-plan.md),不在本期。

## 5. 结果台账

**网格关键行(50 题,seed=42;n=50 全量见 tune_*.json):**

| # | 配置 | r@1 | r@3 | r@5 | p@1 | MRR |
|---|---|---|---|---|---|---|
| 1 | 纯向量 top-4(改造前现状,eval_rag 实测) | 0.51 | 0.70 | 0.72 | 0.52 | 0.602 |
| 2 | 纯向量单路 top-50(参照) | 0.49 | 0.68 | 0.72 | 0.50 | 0.594 |
| 3 | BM25 单路 top-50(参照) | 0.80 | 0.86 | 0.86 | 0.80 | 0.836 |
| 4 | 混合 weighted α=0.5,50/50,**无重排** | 0.71 | 0.92 | 0.96 | 0.72 | 0.824 |
| 5 | 混合 rrf k=5,20/20 + 重排 rc=10(**最低成本达标**) | 0.81 | 0.88 | 0.96 | 0.82 | 0.864 |
| 6 | 混合 weighted α=0.5,50/50 + 重排 rc=20(**生产默认**) | 0.83 | 0.92 | 0.96 | 0.84 | 0.882 |

- 达标配置(R@5≥0.95)共 **18 个**;#6 在达标前提下 r@3/MRR 最优,故取为生产默认。
- 行 1 与行 2 的 r@5 差 1 题:HNSW 对不同 k 的图搜索路径不同(直查 top-4 ≠ 深
  查 top-100 后截断),评测时以各自实际查询方式为准。
- **生产配置复评**(eval_rag.py 走 `get_retriever()` 生产路径,含单例/重排):
  r@1=0.83、r@3=0.92、**r@5=0.96**、p@1=0.84、MRR=0.8823;未命中 2 题(qid 1015、785)。
- **成本实测**:rerank 单批 3 文档 ≈153 prompt tokens,20 候选约 1k tokens/查询,
  按 0.8 元/千 token 计 **<0.001 元/查询**;延迟增加约 0.3-0.6s/次检索。

## 6. 已知局限与偏差

1. **自检索偏差(QA 库评测的通病)**:评测问题就是语料自己的问题文本,BM25 的词面
   优势被放大(行 3 反常地高于行 2)。真实用户会换说法,向量路的实际贡献比此表更大
   ——这正是保留混合而非纯 BM25 的原因。
2. **剩余 2 题未命中**:均为极口语/信息极少的问题;靠 Phase 2 的查询改写(多轮指代
   消解 + 变体扩展)解决,而非继续堆检索超参。
3. **重排分数饱和**:相关性高的块 relevance_score 常贴 1.0,阈值过滤要留神(citations
   展示正常,做 SIMILARITY_CUTOFF 前需重标定)。
4. **加权融合的归一化**是 per-query min-max,单路分数全并列时无区分度(已做保护:
   正分记 1、零分记 0);若未来两路分数分布漂移,可切回 RRF 对比。

## 7. 分点检索(查询拆分,2026-09-03 增补)

> 需求:RAG 不把用户整句一次交给检索,而是**先拆分成多个检索点,逐点检索再融合**
> (即调研方案 Phase 2 的"查询改写/扩展"第一步)。用 Pydantic AI 结构化输出实现。

### 7.1 设计

```
用户问题 ──> 拆分子 agent(decompose_agent,output_type=SubQueries)
             │  Pydantic AI 结构化输出(工具调用模式),温度 0.1
             │  附 ctx.messages 最近 3 条用户原文消解指代;失败/关闭 → 空列表
             ▼
queries = [原始问题, *拆分点(≤DECOMP_MAX_QUERIES=3,去重)]
             │
   每个检索点独立走 §2 的混合召回,并**以该检索点为锚各自重排**
             ▼
合并:前 final_k 名完全由原始问题锚定(与单句检索同序);
     每个拆分点的最佳"新"块追加到尾部进入 LLM 上下文
     (总数 ≤ final_k + 拆分点数 = 5+3)
```

- 拆分子 agent 提示词只允许拆**真实包含的子意图**、每点自包含、≤30 字,单一意图输出
  空列表(此时行为与整句检索完全一致,不浪费重排调用)。
- 开关:`QUERY_DECOMPOSITION=0` 整体关闭;任何拆分失败打 warning 并退回整句检索,
  检索链路永不因拆分环节中断。

### 7.2 合并策略的三次实验迭代(复合问题基准)

复合基准:把评测集两两拼成 20 个"多意图"复合问题(gold=两块并集,只取信息型问题),
对比"同上下文预算"下的 gold 覆盖率(`scripts/eval_compound.py`):

| 合并策略 | 单句@8(对照) | 分点 | 结论 |
|---|---|---|---|
| 跨查询 RRF + 原句锚定重排 | cov 0.858 / both 0.700 | cov 0.717 / both 0.450(合成对) | 复合原句重排偏向句子前半段意图 |
| 逐点重排 + 跨点取最大分 | 同上 | cov 0.808 / both 0.600 | 全局分数排序仍无意图席位保证 |
| 逐点重排 + 名次轮转插值 | 同上 | r@5 0.850,但标准评测 0.96→0.94 | 给拆分点让席位会把单意图 gold 挤出 top-5 |
| **逐点重排 + 原句锚定 + 新块追加(采用)** | **cov 0.858 / both 0.700** | **cov 0.875 / both 0.750,0 负,ctx≈6.8** | 同预算下覆盖最优,且标准评测按构造零回退 |

### 7.3 验证结果

- **标准 50 题评测(--decompose)**:Recall@5=0.96、Precision@1=0.84、MRR=0.8823,
  与关闭拆分时**逐位一致**(零回退;拆分在 50 题中仅对 3 个真多意图问题触发,
  其余输出空列表)。
- **复合问题基准**(20 对,信息型拼对):分点检索覆盖率 cov 0.875 / both 0.750,
  优于同预算的单句深检(0.858 / 0.700),20 对中 1 胜 19 平 0 负。
- **线上冒烟**:三连问("退货流程?运费谁承担?多久退到?")一次返回 6 条引用、
  回答分点覆盖三个子意图;同会话追问正常;e2e 五项回归全绿。
- 成本:每次检索多 1 次拆分 LLM 调用(免费档)+ (1+拆分点) 次 embedding +
  逐点重排调用,单轮增量约 1-2s、<0.005 元。

### 7.4 局限

- 自检索偏差同样压制本功能:gold 与语料问题**逐字重合**时,包含原文的整句天然
  占优,拆分点的改写在词面匹配上反而吃亏(§6.1)。真实用户多意图/带指代的
  场景收益会大于基准显示。
- 拆分质量依赖模型;子 agent 与主 agent 共用 CHAT_MODEL,未单独降档。
